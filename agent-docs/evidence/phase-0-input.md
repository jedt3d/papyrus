# Focus, keyboard and accessibility across three renderers

Checked on 11 October 2026 for [#7](https://github.com/jedt3d/papyrus/issues/7). Web passes the focused keyboard checks. Both Blitz targets support pointer editing, deletion, focus changes around TextInput, disabled guards and access to long content. Button keyboard activation did not work in the recorded Blitz attempts. A painted control is not a keyboard or accessibility guarantee.

## What the APIs actually expose

Web's saved CDP trees expose the `Choose story` navigation name, picker Button names and pressed states, `Press me`, the `Component name` textbox with its associated label/value, disabled flags and focused state. Status nodes expose polite live-region semantics. Those are inspected browser semantics, **not a test of what VoiceOver or another screen reader announces**. The input and Button [raw records](phase-0-input/keyboard-input.json) retain the actual properties, not an invented normalized tree. Disabled flags are in the [Button](phase-0-input/disabled-button.json) and [input](phase-0-input/disabled-input.json) records.

The baseline Blitz launchers keep `default-features = false` and omit `accessibility`. Native AX exposes window chrome; WASM exposes its host canvas/image. This is missing inspection support in these builds, not proof that every Blitz build lacks accessibility. Role/name selectors in the host DOM cannot inspect painted story nodes. CUA accepts pointer/key requests, but does not expose Blitz's focused node or the key that winit actually received.

Pinned source explains two limits. [`stylo.rs:478`](https://github.com/DioxusLabs/blitz/blob/7832c177ff272128154bac58afe56c2b9164b417/packages/blitz-dom/src/stylo.rs#L478) returns false for `:focus-visible`; our custom outline rule cannot match at this pin. Blitz's [default stylesheet](https://github.com/DioxusLabs/blitz/blob/7832c177ff272128154bac58afe56c2b9164b417/packages/blitz-dom/assets/default.css#L93) supplies the visible `input:focus` outline. The [keyboard default handler](https://github.com/DioxusLabs/blitz/blob/7832c177ff272128154bac58afe56c2b9164b417/packages/blitz-dom/src/events/keyboard.rs) handles Tab and text-input editing, with no Button Enter/Space click default action. Our Button supplies `onclick`, so this code supports the observed missing activation path. Exact Button focus still cannot be read in these runtime captures.

Blitz does have public `BaseDocument::get_focussed_node_id`, `focus_next_node` and an optional `build_accessibility_tree`. The current `launch_cfg` wrapper does not give this preview a document inspection handle. The optional [tree builder](https://github.com/DioxusLabs/blitz/blob/7832c177ff272128154bac58afe56c2b9164b417/packages/blitz-dom/src/accessibility.rs#L46) maps roles/text but does not map our disabled, pressed, label-for, input-value and live attributes in that builder. [Accessibility action requests](https://github.com/DioxusLabs/blitz/blob/7832c177ff272128154bac58afe56c2b9164b417/packages/blitz-shell/src/application.rs#L87) are TODO at this pin. These are source inspection findings; the opt-in adapter was not enabled or runtime-tested here.

## Repeat the checks

1. Build the pinned [Web](../../source/README.md), [WASM](../../source/blitz-wasm/README.md) and [Desktop](../../source/blitz-desktop/README.md) launchers. Reset to the named fixture and initial value/count. Record source, CSS, fonts, profile and binary hashes. Use a new window and actual surface/scale samples. Never copy an old coordinate multiplier.
2. Run `pnpm test` from `source/browser-tests/` with the proper Dioxus CLI on PATH. Use `CI=true` with port 8080 free for a fresh server. `input.spec.mjs` walks the picker with actual Tab keys, activates Button with Enter/Space, edits TextInput, attempts disabled controls and checks long controls in a separate narrow viewport. All eight Web tests pass locally. Actions already runs every `*.spec.mjs`; no extra workflow or dependency was added.
3. For Blitz, use the picker labels and visible `Story:` line. For Button, reset with Card → Primary, click empty background, send nine Tabs, Return and Space, then read count. Separately click the Button to prove pointer activation. Record exact Button focus as unknown when there is no inspection handle.
4. For TextInput, pointer-focus the default input and send x/Backspace. Send Shift+Tab and x: it should stay unchanged. Send Tab and x: editing should resume with a visible input outline. Clicking a picker alone is not a verified focus anchor on Blitz; the initial one/two/three-Tab attempts in the raw record did not edit the input. Try disabled fixtures with pointer and keys. Inspect Card/Button long fixtures; use End on the long input and edit/delete at its visible suffix. Read actual received characters rather than assuming the requested key arrived unchanged.
5. Preserve the original images and AX text. Web PNG/DOM checks, Blitz JPEG/visual checks, source inspection and a future human screen-reader check are separate evidence types.

One Web test initially assumed End would collapse the selected long value on macOS; typing replaced it with x. The check was corrected to use the platform's Command+Right shortcut and passed. No component change was needed. Native `typeText("xy")` also left its value unchanged in one separate probe; that API path is unverified. Clipboard support is off, but we have not isolated that tool's delivery path or the cause. The x → U/u → x variation remains unisolated among automation, OS input source, winit and Blitz; it is not silently relabelled as a component failure.

## Recommendation and next work

Keep the Web checks as the first automated input gate. A later Blitz harness should retain a document handle, record the actual focus node and received key/code/modifiers, and pair those with real input plus calibrated captures. Check engine default actions separately from Rust callback wiring. Report `:focus-visible` as unavailable at this pin, the input's UA focus behavior as observed, and accessibility as a separate opt-in profile with role/name/state/action and screen-reader checks. Review these choices in #9 before implementing a permanent adapter.

This completes #7's investigation, including failures and unknowns. It does not make Blitz keyboard or accessibility behavior equivalent to Web. Genuine Thai/IME work remains #8; other OSes, screen readers, opt-in accessibility, narrow Blitz viewports, full focus-order inspection and permanent event/capture adapters remain unverified.
